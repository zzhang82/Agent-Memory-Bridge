## Internal Dynamic State authority MVP

Dynamic State is a narrow internal SQLite/WAL authority lane for one exact-key release state resource. It is not semantic memory, an embedding/FTS feature, a
workflow engine, a distributed state platform, or a new MCP contract.

- `status_transition` applies deterministic release-status transitions.
- `owner_assignment` changes only the declared owner on an existing release
  state.
- `restore` reads an earlier immutable mutation snapshot and appends it as a
  new version; it never rewrites history.
- Every write carries `expected_version` and `expected_database_epoch`.
  Version and restored-database mismatches fail explicitly inside a short
  SQLite write transaction.
- Canonical request identity includes the command, command payload, provenance,
  expected version, and expected database epoch. The immutable
  `state_request_outcomes` ledger persists accepted, conflict, and deterministic
  rejection outcomes for replay on retries.
- Resources, accepted mutations, and terminal request outcomes are immutable.
  The current state head is a rebuildable state-head projection; rebuild derives
  logical `updated_at` from mutation history and validates stored value hashes.
- Thread and process compare-and-swap tests exercise concurrent writers against
  the same SQLite/WAL authority.

Dynamic State does not change recall behavior, FTS, embeddings, ranking, policy,
prompts, ordinary memory, automatic durable writeback, or self-improvement.
Caller provenance remains declared, not authenticated.
